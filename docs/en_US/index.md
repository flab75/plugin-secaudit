# Security audit

The report, rules, summary and alerts follow Jeedom's language, like the interface and this documentation.

Daily security audit of Jeedom and its machine. The report gives a score out of 100 and, for each item, the finding and how to fix it.

How each part works and why: **Documentation** button on the plugin page (`docs/en_US/methodes.md`).

## Usage
- **Wizard**: it asks 5 questions the first time the page is opened (see "Setup wizard").
- Plugin page: **Run the audit** and **Update the database** buttons. The table is sorted by severity, with the issues first.
- Every night (cronDaily), the plugin updates the database then runs the audit again. A new issue of high or critical severity creates a Jeedom message.
- **Configuration** button: whitelist and blacklist, accepted ports, additional database, widget.
- The "Security audit" (« Audit sécurité ») equipment has 5 commands: `score`, `problemes` (issues, not counting "info" items), `resume` (summary text), `graves` (titles of the critical and high issues, or "No serious issues") and the `lancer` (run) action.
  They can be used in a scenario or in the morning report.
- **Widget**: choose the object in the configuration ("Widget (serious issues) shown in"); it shows the serious issues, the score, the Run button (refused to a non-admin account, from the browser or from the API with its key; JeedomConnect does not pass the user, so the app can run it) and, on the dashboard, the "View the audit" button (page restricted to admins). "None", or a deleted object, hides it. The widget shows your weaknesses: place it in an object only admins can see.

## Setup wizard
It opens by itself at the top of the plugin page on the first visit after installation, or after the update to 0.19 (a Jeedom message reminds you of it at installation). It is prefilled with the current settings: running it again loses nothing.

| # | Question | What the answer sets | Advice |
|---|---|---|---|
| 1 | Where should the widget be shown? | `widget_objet`: the "Security audit" equipment is placed in this object and made visible; "Nowhere" hides it | The widget shows your weaknesses: an object only admins can see |
| 2 | Your addresses away from home? | Whitelist (one IP or network per line, `#` for a comment). The "Add my current address" button only appears if you are connected from outside | 4G, office, VPN: if one gets banned, the alert tells you. At most a /24 (IPv4) or a /48 (IPv6) |
| 3 | Are these network-facing services intended and password-protected? | The checked ports are added to "Accepted ports" (never removed) and are no longer reported | Only check a service that asks for a password. The others stay in the audit with their fix |
| 4 | Have you checked the port forwarding on your router? | "Router port forwarding checked" | Only 443 (and 80 for the certificate) should go to Jeedom |
| 5 | Run the first audit now? | Runs the audit (about 1 min) after saving | |

- **Save**: the whitelist is checked first; if it is refused (unreadable address, network too wide, blacklist entry), nothing is saved and the message says why.
- **Later**: closes the wizard without changing anything. In both cases it no longer comes back by itself; the **Wizard** button reopens it.
- Not asked (to be set in Configuration): blacklist, additional rule database.
- If the first audit fails, the answers are already saved: the error is displayed, reload the page.

## Severity and score
The score starts at 100. Each issue removes points according to its severity:

| Severity | Points removed |
|---|---|
| critical | 25 |
| high | 10 |
| medium | 4 |
| info | 0 |

## Rules
- `data/checks.json` is the local database, shipped with the plugin. It contains the configuration tests, the shell tests, the built-in tests, the known vulnerabilities and the fixes.
- `data/checks_remote.json` is generated by "Update the database". It contains:
  - the NVD (NIST) CVEs that target `jeedom:jeedom`. Each one becomes a rule "core version ≤ X" (« version du core ≤ X »);
  - an optional additional database, to be given by URL in the plugin configuration.
- **Security**: a downloaded database can only:
  - make an existing rule more severe (never less severe, nor change its text);
  - add complete rules of type `config` (title, key, known operator) or `core_version` (title, max version), with HTML stripped.

  It can never add a shell command or a fix.

## Fixes
The **Fix** button only appears for fixes written in the plugin. A confirmation is always asked. The old value is saved in `data/sauvegardes.json` and written to the `secaudit` log (the file disappears if the plugin is reinstalled).

| Fix | Effect |
|---|---|
| `api_whiteip` | The rule's API (HTTP, JSON-RPC or TTS) switches to "White IP" (« IP blanche ») mode. Refused if no whitelist entry covers 127.0.0.1 (127.0.0.1, 127.0.0.0/8, 127.*.*.*; read by Jeedom's `netMatch`, for which `127.*` does not cover 127.0.0.1). |
| `whiteips` | Removes from the whitelist the entries wider than a /24 or unreadable (`192.168.1.01-…`, a tab in the middle: `netMatch` would make the range start at 0.0.0.0) (and any IPv6 network: Jeedom's `netMatch` takes a star or an IPv6 range for all of IPv6, and crashes on a prefix > 32), keeps the others, adds `127.0.0.1` and `<local subnet>.*`. |

The other items (SSH, MariaDB, Z-Wave JS UI…) affect the system: the fix describes them, to be done by hand.

## Intrusion attempts and bans
Below the audit, a plain-language summary then one line per IP that probed Jeedom (`log/http.error` log) or that is banned:
- **Who**: owner of the IP (whois done every hour by the cron, kept 30 days) and guessed profile: security company scanner, rented server, VPN, home user (infected machine), your home network, or "unrecognized owner".
- Attempts are kept 30 days per IP (Jeedom's log only keeps ~500 lines).
- "Probably you": an IP from the whitelist, or a French home-user connection that only requested missing Jeedom entry points (installed plugins only), or that Jeedom banned for failed passwords without any suspicious attempt. Never an IP from the blacklist, a hosting provider, a scanner, a VPN, an unrecognized owner, or as long as the whois is not done.
  If it was banned within the last 30 h (Jeedom bans recorded every 5 min, even if lifted since; Unban clears it): red alert, dated from when the ban was first seen, recomputed every hour and after each Unban, and included in the morning report (`alerte_tentatives`). An sshd or recidive ban alone only counts for the whitelist.

## Whitelist and blacklist
In the plugin configuration, one IP or network per line (`203.0.113.7`, `203.0.113.0/24`, `2a01:db8::/48`), `#` for a comment. An unreadable address is refused when saving. In the whitelist, a network wider than a /24 (IPv4) or a /48 (IPv6, one subscriber) is refused too; if entered before 0.12, it is ignored and reported on the page. The blacklist has no width limit, but an added entry is refused if it covers the address you are saving from or an entry of your whitelist (it would cut off the alert that concerns you); likewise, an added whitelist entry covered by the blacklist is refused. Entries already saved are not checked again.
- **Whitelist**: your addresses away from home (4G, office, VPN). If one gets banned, the alert always says so, stating whether it also looked for something other than Jeedom (to check before unbanning). This is not Jeedom's whitelist: it does not prevent banning.
- **Blacklist**: IPs never to be taken for you, even from a French home router. They are not banned for all that. An IP in both lists is treated as blacklisted.

On the page, the IP carries a "whitelist" or "blacklist" tag.
- History of attempts per IP over 30 days: `data/historique.json`.
- **What it was looking for**: goal guessed from the requested paths (theft of secrets, backdoor, diagnostic pages, admin tools, CMS, network devices, missing Jeedom script).
- Attempts, end of ban, **Unban** button (logged in the `secaudit` log). Ban already lifted but still in the alert: **Clear the alert** button (also works if fail2ban no longer responds; its bans are then forgotten after 7 days).
- In the summary, a whitelist IP that looked for something other than Jeedom is counted with the outside addresses.
- Unclassified paths are listed separately: they are the ones used to enrich the families (`FAMILLES` in the class).

**Learning**: every hour, the paths targeted from outside are kept (1000 at most). The `chemins_vises` rule checks
that those that exist here are not served (local request, skipping .php, .phtml, .phar… that PHP would execute; a file restricted to the local network counts as served).
It also reports a PHP script that was missing when a robot requested it and is present now (possible backdoor), checked without executing it; unless it was shipped: for a plugin, content older than the request (the market keeps the archive date); for the core (its `core/`, `desktop/`, `mobile/`, `3rdparty/`, `vendor/`, `install/` folders; never `data/` nor the root), same modification date as `core/config/version` within 10 min, update done after the request. The change date (ctime) is not used: Jeedom resets the permissions of all files at each update. These scripts are forgotten after 90 days.
The log only contains failures: a successful attempt would not appear in it, that is the role of this rule.
Limit: Apache only logs missing files (other than PHP) at `LogLevel info`; at the default `warn` level, only refusals and missing PHP scripts are in `http.error`.

Requires passwordless `sudo` for www-data (standard Jeedom installation) and the `whois` command (installed by the plugin dependencies).

## Data and privacy
The plugin collects nothing for its author and sends no statistics.

**What leaves the machine:**
- The **public IP addresses** that probed Jeedom or were banned, sent to the `whois` servers of the address registries (RIPE, ARIN…) by the hourly cron, at most once per IP every 30 days. An IP from your whitelist that shows up in the log is sent too; local and Tailscale addresses never are.
- A request to the **NVD** (NIST, `services.nvd.nist.gov`) every night, with the keyword `jeedom` only.
- A request to the **additional database**, only if you provide its URL. Its server sees your router's public IP address.

**What is kept on the machine:**

| Data | Where | How long |
|---|---|---|
| Attempts per IP (date, requested paths) | `data/historique.json` | 30 days after the last attempt |
| Owner of each IP (whois) | plugin configuration | 30 days, 300 IPs at most |
| Bans seen | plugin configuration | 30 hours (7 days if fail2ban stops answering) |
| Paths targeted by bots (no IP) | plugin configuration | 1000 paths at most; missing scripts: 90 days |
| Old values before a fix (Jeedom whitelist…) | `data/sauvegardes.json` and `secaudit` log | until reinstall / log rotation |
| Report, whitelist and blacklist | plugin configuration | until uninstall |

Uninstalling removes the plugin configuration; its `data/` files go with its folder.

## Platform
The first line of the report states what Jeedom runs on (VM, Raspberry Pi, Docker or physical machine), with the OS and the versions. On a VM, security also depends on the host, which the plugin cannot see.

## Test
`sudo -u www-data php tests/selftest.php` (refused as root) runs a dry run from the plugin folder; add `en_US` to get the generated texts in English. It checks the remote database safeguard, the log reading and the alert, then evaluates each rule without saving a report. It updates the history, the seen bans and the learned paths, like the cron.
